# 掲示板アプリ 設計書

「世の中のこれがこうだったらいいのに」を自由に投稿できる掲示板アプリ。
このドキュメントは実装前の設計確認用です。コードは含みません。

---

## 1. アプリ全体の設計方針

- **SPA（Single Page Application）+ REST API** という構成にする。
  - **SPA**とは: 最初に1回だけHTMLを読み込み、以降はJavaScriptが画面の中身だけを書き換える方式。ページ全体の再読み込みがないので操作がサクサクになる。
  - **REST API**とは: 「このURLにこの形式でリクエストを送ると、こういうデータが返ってくる」という、フロントとバックエンドの間の通信ルールの一種。
- **3層構成**にする: フロントエンド（見た目・操作） / バックエンド（ロジック・認証・権限チェック） / データベース（データの保存）。それぞれ役割を分けることで、後から「デザインだけ直す」「DBの構造だけ直す」といった変更がしやすくなる。
- **権限チェックは必ずAPI側で行う**。フロント側で「削除ボタンを非表示にする」だけでは、悪意あるユーザーが直接APIを叩けば防げないため。
- **段階的に作る**。DB設計 → バックエンドAPI（Postmanやブラウザで動作確認） → フロントエンド画面、の順に、各段階で動くものを確認しながら進める。

## 2. 使用する技術と選定理由

| 技術 | 役割 | 選定理由 |
|---|---|---|
| **React** | フロントエンドのUI構築 | 画面を「コンポーネント」という部品単位に分割できる。データ（state）が変わると画面が自動で更新される仕組みがあり、手動でのDOM操作が不要。学習情報も豊富。 |
| **TypeScript** | 静的型付け言語（JavaScriptの拡張） | 「この変数は文字列」「この関数はこの形のオブジェクトを返す」といった型を付けられる。コードを書いている最中に間違い（タイプミスや形式の不一致）に気づける。API通信で受け取るデータの形も明確にできる。 |
| **Node.js** | サーバー側のJavaScript実行環境 | フロントと同じ言語（JS/TS）でバックエンドも書けるため、学習の切り替えコストが低い。 |
| **Express** | Node.js用のWebフレームワーク | 「このURLにこのHTTPメソッドで来たらこの処理」というルーティングや、認証チェックなどの共通処理（ミドルウェア）をシンプルに書ける。定番で日本語の情報も多い。 |
| **PostgreSQL** | リレーショナルデータベース | 投稿・コメント・リアクション・タグのように「データ同士のつながり（関連）」が多い構造に向いている。外部キー制約でデータの整合性を保てる。 |
| **JWT (JSON Web Token)** | ログイン状態の認証方式 | サーバー側がログイン状態を覚えておく必要がない（ステートレス）。ログイン時に発行したトークンをクライアントが保持し、以後のリクエストに添付することで「誰か」を判別する。 |
| **bcrypt** | パスワードのハッシュ化 | パスワードを生のまま保存すると漏洩時に危険なため、不可逆な変換（ハッシュ化）をして保存する。ログイン時は入力値をハッシュ化して比較する。 |

## 3. フロントエンド・バックエンド・データベースの構成

```
[ブラウザ] React SPA
     ↕ HTTP(S) / JSON形式、書き込み系リクエストには Authorization: Bearer <JWT> ヘッダーを添付
[Expressサーバー] REST API
     ↕ SQL
[PostgreSQL] データベース
```

### 認証フローの流れ
1. ユーザーがログインフォームでメールアドレス・パスワードを送信
2. サーバーがDBのハッシュ値と照合し、一致すればJWTを発行して返す
3. クライアント（ブラウザ）はJWTを保存する（localStorageなど）
4. 以降、投稿・コメント・リアクションなどのリクエストには `Authorization: Bearer <トークン>` を付与する
5. サーバーは**ミドルウェア**（各APIの処理の前に共通で挟まる処理）でトークンを検証し、`req.user` に「誰が」リクエストしているかをセットする
6. 管理者専用API（ユーザー削除など）では、さらに `role === 'admin'` かどうかをチェックする
7. 停止中ユーザー（`status === 'suspended'`）は、書き込み系API（投稿・コメント・リアクション作成）で拒否する

## 4. フォルダ構成

```
project-root/
├─ frontend/                    # React + TypeScript アプリ（Vite使用）
│  ├─ src/
│  │  ├─ components/            # 再利用可能なUI部品（ボタン、投稿カード、タグ表示など）
│  │  ├─ pages/                 # 画面単位（一覧ページ、詳細ページ、ログインページなど）
│  │  ├─ api/                   # バックエンドと通信する関数をまとめる場所
│  │  ├─ hooks/                 # 状態ロジックを再利用するためのカスタムフック
│  │  ├─ context/               # ログイン状態など、アプリ全体で共有する情報
│  │  ├─ types/                 # フロント側で使うTypeScriptの型定義
│  │  └─ App.tsx                # ルーティングの起点
│  └─ package.json
│
├─ backend/                     # Node.js + Express + TypeScript API
│  ├─ src/
│  │  ├─ routes/                # URLと処理の対応表（例: /api/posts → postsRouter）
│  │  ├─ controllers/           # リクエストを受け取り、処理を実行してレスポンスを返す部分
│  │  ├─ repositories/          # DBへのSQL発行をまとめる場所（controllerから分離）
│  │  ├─ middleware/            # JWT検証、権限チェック、停止ユーザーチェックなどの共通処理
│  │  ├─ db/                    # DB接続設定
│  │  ├─ types/                 # バックエンド側の型定義
│  │  └─ app.ts                 # Expressアプリの起点
│  └─ package.json
│
└─ database/
   └─ migrations/               # テーブルを作るSQLファイル群（変更履歴として管理）
```

**なぜフロントとバックエンドを別フォルダ（別package.json）にするか**: 開発時に使うサーバーが別（Reactは開発用サーバー、Expressは本物のAPIサーバー）で、デプロイ先も分かれるのが一般的なため（フロントは静的ホスティング、バックエンドはNode実行環境）。

## 5. データベース設計

### ER図の考え方（用語説明）
- **エンティティ**: テーブルにあたる「モノ」（例: ユーザー、投稿、コメント）
- **リレーションシップ**: テーブル同士のつながり方
  - **1対多 (1:N)**: 例）1人のユーザーは複数の投稿を持てるが、1つの投稿の投稿者は1人
  - **多対多 (N:N)**: 例）1つの投稿は複数のタグを持てるし、1つのタグは複数の投稿に付けられる → 間に中間テーブルを挟んで表現する
- **主キー (PK)**: そのテーブルの1行を一意に識別するID
- **外部キー (FK)**: 他のテーブルの主キーを指す列。「このコメントはどの投稿に属するか」などを表す

### テーブル一覧

**users**（ユーザー）
| 列名 | 型 | 説明 |
|---|---|---|
| id | PK | |
| username | text | 表示名 |
| email | text (unique) | ログインID |
| password_hash | text | bcryptでハッシュ化したパスワード |
| role | enum('user','admin') | 権限 |
| status | enum('active','suspended') | 停止フラグ |
| created_at | timestamp | |

**posts**（投稿）
| 列名 | 型 | 説明 |
|---|---|---|
| id | PK | |
| user_id | FK → users.id | 投稿者 |
| title | text | |
| body | text | |
| created_at | timestamp | |
| updated_at | timestamp | |

**tags**（タグ・マスタ、固定4種）
| 列名 | 型 | 説明 |
|---|---|---|
| id | PK | |
| name | text | 例: "暮らし", "仕事", "社会", "技術" |
| icon | text | 絵文字（🏠 など） |

**post_tags**（投稿とタグの中間テーブル、多対多を表現）
| 列名 | 型 | 説明 |
|---|---|---|
| post_id | FK → posts.id | |
| tag_id | FK → tags.id | |
| （複合主キー: post_id + tag_id） | | |

**comments**（コメント）
| 列名 | 型 | 説明 |
|---|---|---|
| id | PK | |
| post_id | FK → posts.id | |
| user_id | FK → users.id | |
| body | text | |
| created_at | timestamp | |

**reactions**（リアクション）
| 列名 | 型 | 説明 |
|---|---|---|
| id | PK | |
| post_id | FK → posts.id | |
| user_id | FK → users.id | |
| reaction_type | enum('empathy','like','great','funny','thoughtful') | |
| created_at | timestamp | |
| **ユニーク制約: (post_id, user_id)** | | 1ユーザー1投稿につき1つのリアクションのみ。別の種類を押すとUPDATEで上書きする |

### リレーション概要
```
users (1) ── (N) posts
users (1) ── (N) comments
users (1) ── (N) reactions
posts (1) ── (N) comments
posts (1) ── (N) reactions
posts (N) ── (N) tags   ※ post_tags を介して
```

**リアクションランキング**は専用テーブルを持たず、`reactions` テーブルを投稿ごと・種類ごとに `GROUP BY` で集計するSQLクエリとして実現する。

## 6. API一覧

### 認証
| メソッド | パス | 説明 | 認証 |
|---|---|---|---|
| POST | /api/auth/register | 新規ユーザー登録 | 不要 |
| POST | /api/auth/login | ログイン（JWT発行） | 不要 |

### ユーザー
| メソッド | パス | 説明 | 認証 |
|---|---|---|---|
| GET | /api/users/me | 自分の情報取得 | 要ログイン |
| DELETE | /api/users/:id | ユーザー削除 | 要管理者 |
| PATCH | /api/users/:id/suspend | ユーザー停止/解除 | 要管理者 |

### 投稿
| メソッド | パス | 説明 | 認証 |
|---|---|---|---|
| GET | /api/posts | 投稿一覧（自分の投稿のみ。タグ絞り込み対応） | 要ログイン |
| GET | /api/posts/:id | 投稿詳細（非公開・管理者削除済みは本人と管理者のみ） | 要ログイン |
| POST | /api/posts | 投稿作成 | 要ログイン・要active |
| PUT | /api/posts/:id | 投稿編集 | 本人 or 管理者 |
| DELETE | /api/posts/:id | 投稿削除 | 本人 or 管理者 |
| GET | /api/posts/ranking | みんなのリスト取得（現在は新着順） | 要ログイン |

### コメント
| メソッド | パス | 説明 | 認証 |
|---|---|---|---|
| GET | /api/posts/:id/comments | コメント一覧（見られる投稿のみ） | 要ログイン |
| POST | /api/posts/:id/comments | コメント投稿 | 要ログイン・要active |
| DELETE | /api/comments/:id | コメント削除 | 本人 or 管理者 |

### リアクション
| メソッド | パス | 説明 | 認証 |
|---|---|---|---|
| POST | /api/posts/:id/reactions | リアクションを付ける/変更する | 要ログイン・要active |
| DELETE | /api/posts/:id/reactions | 自分のリアクションを外す | 要ログイン |

### タグ
| メソッド | パス | 説明 | 認証 |
|---|---|---|---|
| GET | /api/tags | タグ一覧（固定4種） | 不要 |

## 7. 開発ステップ

| 0 | 環境構築（Node.js, npm, PostgreSQL, VSCode拡張機能のインストール） |

## この設計に対する前提・決定事項（確認済み）
- リアクションは1ユーザー1投稿につき1種類のみ（変更すると上書き）
- 一般ユーザーは自分のコメントを削除できる（投稿と同じ権限モデル）
- 停止されたユーザーはログインはできるが、投稿・コメント・リアクションの作成はできない
